# 规模效应、并发与版本兼容

这份文档回答三个"真拿去用"才会冒出来的问题：

1. 规模效应到底有多大——**以及它在什么前提下才成立**；
2. MCP 服务器阻塞会不会吃掉规模效应；
3. 别人的 MATLAB 不是 R2024b 还能不能跑。

> 下面所有数字都来自本机实测（motor-valve benchmark 模型，10 s 仿真时长，20 次实验），
> 只有"LLM 往返 3 s"是假设，已标注。

---

## 1. 先看实测：时间都花在哪

| 环节 | 实测 |
| :--- | ---: |
| 一次仿真（Fast Restart 热态） | **0.09 s** |
| 一次决策（MATLAB 内手写前向） | **0.002 s** |
| MATLAB 冷启动（`matlab -batch "disp(1)"`） | **50 s** |
| 模型首次编译（Simscape 多体） | **~10 s** |

于是同一个任务（20 次实验）有四种跑法：

| 跑法 | 每次任务 | 20 次实验 | 说明 |
| :--- | ---: | ---: | :--- |
| Agent 在环（LLM 3 s/次） | 60 s | 60 s | 每步等一次语言模型 |
| **一次 CLI 进程一个任务** | 122 s | 122 s | 50 s 启动 + 10 s 编译 + 调参 |
| 常驻 worker（MATLAB 不退出） | 15 s | 15 s | 启动只付一次 |
| 常驻 + 模型已编译复用 | **~2 s** | **~2 s** | 省掉每次重新编译 |

**结论很硬：如果每个任务都新起一个进程，这个项目比 Agent 在环还慢。**
规模效应不是自动成立的——它依赖"MATLAB 常驻 + 模型复用"。

### 换成批量看

| 任务数 | Agent 在环 | 一进程一任务 | 常驻 worker | 常驻 + 模型复用 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 1 min | 2 min | 1 min | 1 min |
| 100 | 1.7 h | 3.4 h | 25 min | **3.3 min** |
| 1 000 | 17 h | 34 h | 4.2 h | **33 min** |

（worker 一列按 15 s/任务、复用一列按 2 s/任务线性外推；实际会受 MATLAB 许可证并发数限制。）

**这正是大型项目值得参考的地方**：不是"决策快 0.19 ms"，而是**把 N×M 次
LLM 调用换成 1 次工具调用 + N×M 次 0.002 s 的本地决策**，前提是会话保持热态。

## 2. 阻塞的 MCP 会不会吃掉规模效应？

**不会——但真正的瓶颈不是阻塞，是冷启动和重编译。**

- 阻塞只是让任务排队：一次 15 s 的任务，1 000 个串行 = 4.2 h，仍然比 Agent 在环的 17 h 快 4 倍。
- 但如果每个任务都新开 MATLAB，1 000 个 = 34 h，**反而更慢**。

所以当前实现做了两件事：

1. **MCP 的 `tune_simulink` 走常驻 worker**（`src/jev_tune/matlab_worker.py`）：进程内的单例，第一次调用启动 MATLAB，之后复用；
2. **`jev-tune batch --jobs jobs.json`**：一个进程里顺序跑一整个队列，启动只付一次。

还差的最后一块是**模型编译复用**：现在每个任务都会复制模型到新的 scratch 目录并重新编译（~10 s）。如果同一个模型要跑很多次（同一台设备的多个工况），应该只编译一次。这是下一步最划算的优化。

并发仍然有三种选择，按代价排序：

| 方案 | 收益 | 代价 |
| :--- | :--- | :--- |
| **A. 多 worker 进程**（推荐） | 线性加速 | 受 MATLAB 许可证并发数限制，内存 ×N |
| B. `parsim` 批处理 | 无许可证问题 | 只适合"批量评估"，不适合"看一步走一步"的闭环 |
| C. 多 MCP 实例 | 零改动 | 需要客户端支持并发 |

## 3. 版本兼容：别人不是 R2024b 怎么办

原来的代码有两处硬假设：MATLAB 装在 `C:\Program Files\MATLAB\R2024b`，以及
`matlab -batch` 一定可用。两处都已修掉。

**发现顺序**：`MATLAB_EXE` → `PATH` → Windows 注册表（`HKCU\Software\MathWorks\MATLAB`）
→ 常见安装目录扫描 → POSIX 路径（`/usr/local/MATLAB/*`、`/Applications/MATLAB_R*.app`）。

**启动器**：探测 `matlab -help` 是否含 `-batch`，没有就退回 `-nodisplay -nosplash -r "…; exit"`。

**能力探测**（`jev-tune matlab --probe`，或 MCP 的 `tune_probe_matlab`）：

```json
{"release": "2024b", "has_fast_restart": true, "has_scope_logging": true,
 "has_pid_tune": true, "supports_batch": true}
```

**版本下限**（按用到的 API 推算）：

| 功能 | 最低版本 | 说明 |
| :--- | :--- | :--- |
| Fast Restart | R2013b | 没有它也能跑，只是每次重编译，慢 8–19× |
| Scope 数据记录 | R2014a | 否则需要改成 To Workspace |
| `jsonencode/jsondecode` | R2016b | 桥接层用，低于此版本需换 CSV |
| `-batch` | R2019a | 低于此版本自动退回 `-r` |
| 决策头前向 | 任意 | 纯矩阵运算，无工具箱依赖 |

**实测范围**：只有 R2024b 真正跑通。其他版本靠探测 + 降级逻辑，**未逐一验证**——
这一点必须如实说，不要让人以为"全版本支持"。

## 4. 产品逻辑不一致清单（自查）

| # | 问题 | 影响 | 状态 |
| :--- | :--- | :--- | :--- |
| 1 | MATLAB 路径写死 R2024b | 换版本直接失败 | ✅ 已修（自动发现） |
| 2 | 增益块/示波器名写死 | 别人的模型跑不了 | ✅ 已修（`cfg.kp_block` 等） |
| 3 | `matlab -batch` 假设 R2019a+ | 老版本失败 | ✅ 已修（回退 `-r`） |
| 4 | 每个任务重开 MATLAB（50 s） | 规模效应直接归零 | ✅ 已修（常驻 worker + batch） |
| 5 | **每个任务重编译模型（~10 s）** | 每任务从 2 s 变 15 s | ⚠️ 未修（下一步最划算） |
| 6 | 只支持"三个独立增益块"的并联 PID | 用 `PID Controller` 块的模型无法直接调 | ⚠️ 未修（需 block adapter） |
| 7 | 代价函数固定为阶跃指标 | 跟踪/扰动抑制项目不适用 | ⚠️ 未修（需新增 metric） |
| 8 | 参考值默认来自 `Step × Deg2Rad` | 非阶跃输入会算错 | ✅ 已支持 `cfg.ref_source` |
| 9 | 训练分布是 10 s / 5 ms 的阶跃响应 | `StopTime` 差太远时特征失真 | ⚠️ 未加警告 |
| 10 | 名字叫 `jev-tune` | 容易被误解为"用了 Jev 模型" | ✅ README 已显式澄清 |

剩下四条（5、6、7、9）的优先级：

1. **#5 模型编译复用** —— 直接决定批量吞吐，改动集中在 `jev_tune_model` 的生命周期；
2. **#7 代价函数可配置** —— 最常见的需求（跟踪 / 扰动抑制）；
3. **#6 PID Controller 块适配** —— 决定能否开箱用于别人的模型；
4. **#9 分布漂移警告** —— 便宜，避免"默默给出错误建议"。
